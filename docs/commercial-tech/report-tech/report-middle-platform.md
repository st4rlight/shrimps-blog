# 报表中台技术体系

> 当业务方第 N 次说"这个报表加个字段""那个指标口径不对""能不能给个接口让前端直接拉"，而你每次都要改 SQL、发版、等上线——你就会意识到：报表不该是一个个散落各处的查询，而是一套**可管理的体系**。

## 一、什么是报表中台

### 1.1 它要解决什么问题

传统报表开发里，三样东西通常是割裂的：

- **物理表**：落在数仓 / HBase / MySQL 里的真实表，谁建的、字段啥含义、血缘从哪来，往往没人说得清；
- **视图**：业务真正想要的"虚拟表"，是物理表之上的一层语义抽象，但大多只存在于某个 BI 工具的临时查询里，不可复用；
- **API**：前端 / 其他系统要消费数据，最后又得单独写接口把 SQL 包一层。

这三层各管各的，改一处牵全身。报表中台要做的，就是把这三样**统一管理**起来。

### 1.2 核心定位

一句话：

> **报表中台是一个能够统一「管理物理表、视图、以及 API」的系统。**

它把"数据在什么表里"（物理表）、"业务怎么看这些数据"（视图）、"外部怎么取这些数据"（API）这三层，收拢到一个平台里，用一致的元数据驱动。

## 二、三大管理对象

### 2.1 物理表管理

物理表是中台的"地基"。中台需要对每张物理表登记元数据：

- 所属数据源（MySQL / Hive / ClickHouse / ...）
- 字段、类型、注释、负责人
- 数据血缘与更新频率

这部分通常是**注册 + 发现**的能力，让"有哪些表、表从哪来"变得可查、可控。

### 2.2 视图层（逻辑表）

视图是物理表之上的**逻辑抽象层**。业务方不直接面对物理表，而是面对一个个有意义的"视图"：

- 一个视图可以跨多张物理表 join、聚合；
- 视图可以再基于视图定义（分层建模）；
- 视图对用户呈现的是干净的语义，背后复杂的物理细节被屏蔽。

视图层是中台最有价值、也最需要"算得聪明"的一层——因为它是查询真正发生优化的地方。

### 2.3 API 管理

API 是数据对外暴露的出口。中台把"某个视图 → 某个 HTTP 接口"的关系配置化：

- 选择视图、定义入参（分页、筛选）、生成接口；
- 调用方拿接口取数，不用关心底层 SQL 和存储。

这样，新增一个取数接口 ≈ 配置一个视图 + 一条 API 规则，而不是写一套新服务。

## 三、视图层为何选择 Apache Calcite

视图层的核心是：**把用户写的（或平台定义的）查询，翻译成对物理数据源最高效的执行计划**。这件事，Apache Calcite 是最合适的引擎。

### 3.1 Calcite 是什么

Apache Calcite 是一个**动态数据管理框架**，它本身不存储数据，而是提供：

- SQL 解析（Parser）
- SQL 校验（Validator）
- 关系代数（RelNode）
- 查询优化器（Planner，支持 RBO / CBO）
- 可插拔的适配层（Adapter）

换句话说，Calcite 是"查询的大脑"，数据源只是它外接的"手脚"。

### 3.2 SQL 解析与校验

用户在前端定义一个视图，本质是一段 SQL。Calcite 先把它解析成抽象语法树（AST），再做语义校验——字段存不存在、类型匹不匹配、函数合不合法，在**查询执行之前**就兜住错误，而不是等查挂了才发现。

### 3.3 关系代数与优化器

校验通过后，SQL 被转换成关系代数（RelNode）。Calcite 的优化器在这里施展拳脚：

- **基于规则的优化（RBO）**：下推过滤条件（Filter Pushdown）、列裁剪（Projection Prune）、谓词合并等，由 `HepPlanner` 按既定顺序确定性地应用规则；
- **基于代价的优化（CBO）**：由 `VolcanoPlanner` 结合统计信息，枚举等价执行计划、选择 join 顺序与访问路径，追求总成本最低。

这正是"视图层使用 Calcite 进行优化建设"的含义——视图不是简单的 SQL 字符串存档，而是经过 Calcite 优化后生成的、可高效落地的执行计划。

### 3.4 适配层与多数据源

Calcite 通过 Adapter 屏蔽底层差异。同一份视图定义，可以对接 Hive、MySQL、ClickHouse 等不同物理数据源；Calcite 借助各数据源的 Adapter（如 JDBC / 各引擎的 RelToSql 转换），把优化后的 RelNode 下推或转换为对应执行计划（SQL 方言或原生算子）。这让中台天然支持**多源异构**。

### 3.5 在中台里怎么用（示意）

一个典型的视图优化流程：

```java
// 1. 配置 Calcite：连接物理数据源的 schema，挂载 RBO 优化规则
//    Programs.ofRules(...) 直接接收 RelOptRule，无需再用 RuleSets.ofList 包裹
FrameworkConfig config = Frameworks.newConfigBuilder()
    .defaultSchema(schema)            // 物理表元数据
    .parserConfig(SqlParser.Config.DEFAULT)
    .programs(Programs.ofRules(
        CoreRules.FILTER_INTO_JOIN,   // 过滤下推：把 Join 上方的过滤条件下推
        CoreRules.PROJECT_MERGE       // 投影合并：合并相邻的 Project 算子树
    ))                                // 该 program 基于 HepPlanner（RBO）
    .build();

// 2. 把一个视图定义（SQL）解析、校验、优化
Planner planner = Frameworks.getPlanner(config);
SqlNode sqlNode = planner.parse(
    "SELECT u.name, SUM(o.amount) " +
    "FROM users u JOIN orders o ON u.id = o.uid " +
    "GROUP BY u.name");
sqlNode = planner.validate(sqlNode);
RelNode relNode = planner.rel(sqlNode).rel;   // 关系代数（RelRoot.rel）+ 已应用 RBO 优化

// 3. relNode 经 Adapter 下推/转换为具体数据源的执行计划后下发
```

视图在注册进中台时跑一遍上述流程，得到优化后的计划并缓存；运行时命中视图直接复用，避免重复解析与优化。

### 3.6 视图的物化：从"即时计算"到"预计算"（进阶）

当视图被高频查询、但底层物理表很大时，每次都现场优化 + 扫描会很重。业界（如 Cube）的成熟做法是**物化视图 / 预聚合（pre-aggregation）**：把常用视图的查询结果提前算好、落盘存储，查询时直接命中物化结果，做到亚秒级响应。

在 Calcite 体系里，物化视图对应 `MaterializedViewRule` 等规则：优化器能识别"当前查询已被某个物化视图覆盖"，从而把查询改写为对物化表的读取，而不是重算底层大表。中台可据此提供"视图定义 → 自动选物化策略"的能力，是视图层优化的进阶形态。

## 四、整体架构示意

```
                ┌─────────────────────────────┐
   业务方/前端 ──▶│         API 管理层           │
                │  (视图 → HTTP 接口配置化)     │
                └──────────────┬──────────────┘
                               │ 引用
                ┌──────────────▼──────────────┐
                │        视图层（逻辑表）        │
                │  ── Apache Calcite 解析/校验/优化 │
                └──────────────┬──────────────┘
                               │ 映射
                ┌──────────────▼──────────────┐
                │       物理表管理层           │
                │  (多源元数据 / 血缘 / 注册)   │
                └──────────────┬──────────────┘
                               │ Adapter 适配
                ┌──────────────▼──────────────┐
                │  MySQL / Hive / ClickHouse … │
                └─────────────────────────────┘
```

三层各司其职，Calcite 串起视图层的"算"，API 层解决"取"，物理表层解决"存与管"。

## 五、业界参考：这其实就是"语义层（Semantic Layer）"

如果把上面这套体系放到业界坐标系里看，它本质就是近年火热的数据**语义层（Semantic Layer）**——一个位于数据仓库与消费方（BI / API / AI）之间、用一致方式定义指标、维度、关联与口径的治理层。

- **dbt Semantic Layer（MetricFlow）**、**Cube**、**LookML（Looker）**、**AtScale** 都是这一模式的代表：把业务语义（"营收""活跃用户"到底怎么算）定义在代码里、纳入版本管理，再统一对外暴露为可查询的 API。
- 现代语义层强调 **Headless（无头）**：定义一次、处处消费——同一份口径既能喂 BI 看板，也能喂前端嵌入分析，还能喂给 AI 助手做可信的 text-to-SQL。
- 它的核心价值正是解决**口径漂移（metric drift）**：全公司问"Q3 营收"只会有一种答案，而不是每个仪表盘各算各的。

所以"报表中台 = 物理表 + 视图（Calcite 优化）+ API"这套设计，并不另类，而是与业界主流语义层同构；区别只在于我们把"视图层用 Calcite 做优化建设"作为中台自己可控的技术选型，而不是完全依赖某个商业语义层产品。

## 六、小结

报表中台的本质，是把"报表"从**一次性的 SQL 查询**，升级为**可治理的数据资产**：

- 物理表管"有什么数据"；
- 视图层（借 Calcite）管"怎么高效地把数据变成业务语义"；
- API 管"怎么把数据安全地交出去"。

三者统一在一个平台里，报表的需求变更，从"改代码发版"变成"配视图、配接口"。
