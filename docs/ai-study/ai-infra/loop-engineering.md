# Loop Engineering解析

> 参考资料：
> - Boris Cherny（Claude Code 负责人）访谈分享（2026.06）
> - Peter Steinberger（OpenClaw 创始人）推文（2026.06.08）
> - LangChain 博客《循环工艺：堆叠循环的艺术》（loopcraft）
> - 清华大学清新研究团队《2026 循环工程研究报告》

## 一、从"写 Prompt"到"设计循环"

### 1.1 两个关键人物的宣言

2026 年 6 月，AI 工程领域出现了两条几乎同时发出的宣言，把一个新范式推到了台前。

第一句话来自 Boris Cherny——Claude Code 的创建者和负责人：

> "1 年前我写代码的方式，是在 IDE 里配合某种自动补全功能。去年 11 月，我卸载了 IDE。那个时候，我可能同时跑着 5 到 10 个 Claude，我所谓的写代码就是提示 Claude 去写代码。**现在，我觉得又到了下一个层级：我不再提示 Claude 了，我有一堆循环在运行，它们才是在提示 Claude 并判断接下来该做什么。我的工作变成了写循环。**"

第二句话来自 Peter Steinberger——OpenClaw 创始人，后加入 OpenAI：

> "你不应该再给编程 Agent 写提示词了。你应该设计一套循环机制，让这些循环去提示你的 Agent。"

这条推文在一周内获得了超过 500 万次浏览，引发了开发者社区的广泛讨论。Peter 随后回应说："不用担心，大概还需要 3 个月才会到那一步，之后人们将讨论'设计你的 loops 的舰队'。"

这两段话共同指向一个趋势：**开发者的角色正在从"指令发送者"转变为"循环系统设计者"**。社区开始把"写 Loop"视为继"写 Prompt"之后的下一层抽象，也有人把这种变化概括为"从 prompt engineer 到 meta-prompt engineer"。

### 1.2 抽象层级的爬升

理解 Loop Engineering，必须先理解它身处的那条演化链。每一层都是包住前一层的，而不是单纯的替代：

![AI交互范式四层演进](/ai-study/loop-engineering/paradigm-evolution-overview.svg)

| 阶段 | 时间 | 核心问题 | 开发者角色 |
|------|------|---------|-----------|
| **Prompt Engineering** | 2022-2024 | 怎么跟模型说话？ | 优化措辞、加 few-shot 示例 |
| **Context Engineering** | 2025 | 模型推理时需要看到什么？ | 策划 RAG、上下文压缩、token 预算 |
| **Harness Engineering** | 2026 | Agent 运行需要什么环境？ | 配置工具、约束条件、反馈管道 |
| **Loop Engineering** | 2026 | Agent 如何持续自主工作？ | 设计驱动自主工作的迭代循环 |

口诀很简单："措辞 → 上下文 → 环境 → 循环"，杠杆率一层比一层大。

但需要强调的是，这四个阶段不是替代关系，而是**嵌套关系**——Loop Engineering 包住 Harness Engineering，Harness Engineering 包住 Context Engineering，Context Engineering 包住 Prompt Engineering。你仍然需要写好 prompt、管理好上下文、搭好 harness，只是你的关注点从"单次交互"上升到了"持续循环"。

### 1.3 为什么是现在？

Loop Engineering 是两条独立发展趋势的汇集产物。

**第一条线索：Agent 框架的内卷。** 2024 年我们还在争论 LangChain vs. 裸调用 API，2025 年 Claude Code、Codex、Grok 把 tool-use 推进到了生产级水平。到 2026 年，"一个 Agent 能做什么"已经不是问题了，问题是"一个 Agent 能持续做什么"。单次会话的能力见顶后，大家开始关注跨会话的持续性。

**第二条线索：人类瓶颈。** 很多人使用 Coding Agent 的方式，其实早就不是一次性问答了。更常见的节奏是：先丢给 Agent 一个目标，等它跑完；人再回来读结果、挑问题、补 Prompt、重跑测试；如果还不满意，就继续追加要求。这个过程看起来像一串离散对话，本质上却是一条 Agent Loop：观察现状，决定下一步，执行修改，验证结果，再根据验证结果回到下一轮。

问题在于，过去这条链路里最忙的不是 Agent，而是人——人被放在了最密集的折返点上。注意力被不断打断，你刚切去写文档，Agent 跑完了；你回来扫一眼，发现测试红了；你写下一段 Prompt 让它修，它修完又出了别的问题。你在"保姆"一个本来应该替你工作的东西。

Loop Engineering 讨论的核心问题就在这里：**如果 Agent 已经能执行、能读结果、能写代码、能跑测试，为什么还一定要让人守在循环体里？**

## 二、Loop Engineering 是什么

### 2.1 一句话定义

> **Loop Engineering 是面向 AI Agent 和自动化系统的反馈闭环设计方法，通过状态管理、工具执行、外部观察、评估信号、纠错策略和停止条件，让模型从"一次性生成"升级为"可迭代完成任务"。**

它解决的不是"模型会不会说"，而是"任务做完一步后，下一步该干什么"。

### 2.2 从一次性回答到反馈闭环

很多人第一次做 Agent，会把流程写成这样：

```
用户输入 → 大模型生成答案 → 返回结果
```

这适合问答，但不适合执行任务。真实业务里的 Agent 经常遇到这些情况：

| 场景 | 一次性回答的问题 | 需要 Loop 的原因 |
|------|----------------|-----------------|
| 写代码 | 代码看起来对，但测试失败 | 要读取报错、定位原因、修改、再测试 |
| RAG 问答 | 答案流畅，但证据不支持 | 要重新检索、交叉验证、拒答或追问 |
| 工具调用 | API 返回 500 或字段缺失 | 要区分临时错误、参数错误、权限错误 |
| 自动运维 | 指标异常，但原因不确定 | 要观察日志、指标、变更记录并逐步收敛 |
| 内容生成 | 初稿完整，但质量分不高 | 要根据结构、深度、可读性反馈迭代 |

所以 Agent 工程的关键，不是让模型"想得更多"，而是让它做完一步后知道下一步该干什么。这就是 Loop Engineering 的价值。

### 2.3 与 Harness Engineering 的关系

Loop Engineering 和 Harness Engineering 容易混淆，但它们关注的层次不同：

- **Harness Engineering** 关注的是"给定一个任务，如何帮助 Agent 可靠地完成它"——搭建工具、约束、反馈管道、沙箱、权限等运行环境。
- **Loop Engineering** 关注的是"Agent 接下来应该做什么，以及如何让它持续、自主、可控地运行"——设计触发机制、跨会话状态、监控反馈和持续改进。

用一个比喻：Harness 是 Agent 的"运行时环境"，Loop 是包裹在 Harness 外面的"调度系统"。Harness 回答"怎么把一件事做好"，Loop 回答"接下来做什么事、做完了怎么办、做砸了怎么办"。

## 三、双层循环架构：内循环与外循环

![双层循环架构](/ai-study/loop-engineering/dual-loop-architecture.svg)

理解 Loop Engineering 的关键，是理解 Agent 系统包含两个嵌套层级的循环。

### 3.1 内循环（Agent Loop）：把给定任务做好

内循环就是大家熟悉的 Agent 运行时——Claude Code、Codex 等。你给 Agent 一个任务，它读取相关上下文，使用工具，执行工作，检查结果，直到任务完成。

```
给定任务 → 读取上下文 → LLM 推理 → 调用工具 → 获取结果 → 检查是否完成
    ↑                                                        |
    └──────────────────── 未完成 ←─────────────────────────────┘
```

内循环回答的问题是：**给定这个任务，我们如何帮助 Agent 可靠地完成它？**

目前大多数 Agent 优化都在这一层：更好的上下文和指令、技能和工具定义、任务分解、工具使用。但它仍然依赖于有人来决定"这是一个值得做的任务"。这就是外循环发挥作用的地方。

### 3.2 外循环（Outer Loop）：决定接下来做什么

外循环围绕 Agent 运行时，负责以下事项：

| 职责 | 说明 |
|------|------|
| **触发** | 什么应该唤醒 Agent？定时器、事件、队列、手动？ |
| **状态保持** | 跨会话应保留什么状态？记忆、进度、经验？ |
| **信息共享** | 不同 Agent 如何共享信息？共享经验池、消息总线？ |
| **结果监控** | 如何评估输出质量？评分器、人工审核、自动验证？ |
| **持续改进** | 系统如何随时间变好？反馈回流、技能沉淀、CLAUDE.md 更新？ |

外循环回答的问题是：**Agent 接下来应该做什么，以及如何让系统随时间改进？**

### 3.3 内外循环的协作

一个完整的 Loop Engineering 系统是内外循环的嵌套：

```
外循环：触发 → [内循环：任务执行] → 验证 → 反馈 → 改进 → 触发
```

内循环负责"把一件事做对"，外循环负责"做对的事并持续改进"。两层循环各自有独立的停止条件、重试策略和反馈机制，互不干扰但相互支撑。

这种分层设计带来了一个关键优势——**分层弹性**：内循环可以做局部重试（某个工具调用失败就重试），外循环可以做全局调整（任务方向偏了就重新规划），避免了单层循环的僵化。

## 四、Loop Stack：循环系统的六大组件

![Loop Stack 六大组件](/ai-study/loop-engineering/loop-stack-overview.svg)

清华大学清新研究团队在 2026 年 6 月发布的循环工程研究报告中，提出了 Loop Stack 的六件套框架，描述了一个完整的 Loop Engineering 系统需要的基础设施：

| 组件 | 功能 | 典型实现 |
|------|------|---------|
| **Automations** | 任务调度与心跳唤醒 | cron 定时器、事件触发器、webhook |
| **Worktrees** | 多 Agent 并行隔离 | git worktree、独立工作目录、容器隔离 |
| **Skills** | 项目知识与流程沉淀 | CLAUDE.md、技能文件、SOP 文档 |
| **Connectors** | 外部系统连接器 | MCP 服务器、API 集成、数据库连接 |
| **Sub-agents** | 子智能体委派 | Task 工具、多 Agent 协调、委派机制 |
| **Memory** | 跨循环持久记忆 | 向量数据库、事件日志、经验池 |

### 4.1 Automations：让循环自己转起来

Automations 是外循环的"心脏"，负责决定什么时候唤醒 Agent。它可以是：

- **定时触发**：每天凌晨跑一次代码审查循环
- **事件触发**：CI 失败时自动启动修复循环
- **心跳触发**：每隔 5 分钟检查一次任务队列

OpenClaw.NET 的 `/loop` 命令就是一个典型的 Automation 实现——用户输入 `/loop 5m check CI status`，系统就会每 5 分钟自动注入提示词，驱动 Agent 持续执行任务，直到满足终止条件。

### 4.2 Worktrees：让多个循环并行不冲突

当你同时运行多个 Agent 循环时，最大的问题是冲突——两个 Agent 同时改同一个文件。Worktrees 通过 git worktree 或独立容器为每个 Agent 循环提供隔离的工作空间。

Boris Cherny 的做法是：在终端里同时运行 5 个 Claude 窗口，每个本地会话使用自己的 git checkout，而不是分支或工作树。同时在网页端运行 5-10 个会话，用 `--teleport` 命令在本地和云端之间"传送"进度。

### 4.3 Skills：让循环越跑越聪明

Skills 是循环系统的"记忆载体"。每次循环跑完后，有价值的经验应该被沉淀下来，供下一次循环使用。

Anthropic 团队的做法是：每个团队在 git 中维护一个 CLAUDE.md 文件，团队成员每周多次更新。只要发现 Claude 哪里做错了，就把规矩写进 CLAUDE.md。Boris 经常在同事的 PR 上使用 `@.claude` 标签，将学习成果添加到 CLAUDE.md 中，确保每个 PR 的知识都被保存下来。

### 4.4 Connectors：让循环连接真实世界

Connectors 让循环系统不再是孤岛。通过 MCP 协议或 API 集成，Agent 循环可以读取数据库、调用外部服务、操作文件系统、提交 PR。Connectors 是循环系统的"手脚"——没有它们，循环只能在自己内部打转。

### 4.5 Sub-agents：让循环可以分身

当一个循环任务太复杂时，可以委派给子 Agent 处理。Claude Code 的 Task 工具就是典型的 Sub-agent 机制——一次指令、一份报告、独立会话 ID、并行上限 10。子 Agent 完成任务后将结果汇报给主循环，主循环根据结果决定下一步。

### 4.6 Memory：让循环拥有过去

Memory 是跨循环的持久记忆。单次会话的上下文窗口是临时的，但循环系统需要跨会话的经验积累。Memory 可以是：

- **事件日志**：记录所有交互（类似 Managed Agents 的 Session）
- **向量记忆**：对关键决策做语义嵌入，支持语义检索
- **共享经验池**：多个 Agent 循环共享一个经验 Collection

## 五、循环堆叠的艺术：从 Agent Loop 到验证循环

Loop Engineering 的精髓不只是"一个循环"，而是**循环的堆叠**。LangChain 提出的"循环工艺"（loopcraft）理念，核心思想是你可以堆叠并扩展多个循环，从而构建出更高效的 Agent。

### 5.1 第一层：Agent 循环

最基本的循环——一个模型在循环中调用工具，直到任务完成：

```
任务 → LLM 规划 → 调用工具 → 获取结果 → 判断是否完成 → (未完成) → LLM 规划
```

这一层解决了"Agent 能做事"的问题，但不保证做得对。

### 5.2 第二层：验证循环

Agent 循环能完成工作，但并非每次都能在第一次尝试就产生正确或一致的结果。当结果一致性至关重要时，需要将其包装在验证循环中：

```
Agent 循环产出 → 评分器检查 → 合格？
    ├─ 是 → 输出结果
    └─ 否 → 反馈 + 原始结果 → 重新进入 Agent 循环
```

验证循环增加了一个评分器（Grader）：它根据评估标准检查 Agent 的输出，如果失败，则将结果连同反馈一起发回。评分器既可以是确定性的（如单元测试、lint 检查），也可以是智能体式的（LLM 作为评判者）。

### 5.3 第三层及更深：支持循环、长期记忆循环

在验证循环之上，还可以继续堆叠：

- **支持循环**：当 Agent 遇到障碍时，自动检索相关文档或历史经验，注入上下文后重试
- **长期记忆循环**：每次循环结束后，将关键决策和经验嵌入向量存储，供未来循环检索
- **协调循环**：多个 Agent 循环并行工作，由协调器分配任务、汇总结果

```
协调循环 → [Agent循环 → 验证循环 → 支持循环] × N → 汇总 → 长期记忆更新
```

这种堆叠不是理论构想——LangChain 已经提供了对应的原语来实现每一层。循环的每一次堆叠，都在为系统增加一层"自我纠错"的能力。

## 六、关键设计原则

### 6.1 执行与决策分离

好的循环系统应该把"执行层"和"决策层"分开。执行层只负责调用工具、产出结果，不做策略判断；决策层只负责验证产出、决定路由，不直接执行。

这种分离的好处是：执行层可以专注于"把事情做对"，决策层可以专注于"做对的事情"。两者职责清晰，不会互相干扰。

### 6.2 有边界的循环优于开放循环

开放循环（目标模糊，无明确终止条件）容易失控——Agent 不知道什么时候该停，越跑越乱。有边界的循环通过明确的停止条件来约束 Agent 行为：

| 停止条件类型 | 示例 |
|-------------|------|
| 成功条件 | 测试全部通过、质量分 ≥ 0.8 |
| 失败条件 | 连续 3 次重试失败、成本超限 |
| 时间边界 | 最多运行 30 分钟 |
| 步数边界 | 最多迭代 10 轮 |

### 6.3 分层弹性

内循环做局部重试，外循环做全局调整。当内循环遇到工具调用失败时，直接重试这个步骤即可，不需要重启整个任务；当外循环发现任务方向偏离时，可以重新规划而不影响内循环的执行效率。

### 6.4 动态技能发现

不要一次性把所有技能塞给 Agent，而是根据当前任务按需加载。这既节省了上下文窗口，也减少了无关信息对 Agent 决策的干扰。

### 6.5 反馈是燃料

一个循环如果没有反馈机制，就是在空转。好的循环系统必须设计清晰的反馈通道：

- **执行反馈**：工具调用结果、测试输出、lint 报告
- **质量反馈**：评分器打分、人工审核意见
- **经验反馈**：历史决策的成败记录、模式识别结果

反馈越及时、越精确，循环的收敛速度就越快。

## 七、实战模式

![手动提示 vs 循环驱动对比](/ai-study/loop-engineering/manual-vs-loop-comparison.svg)

### 7.1 PR 自动修复循环

一个典型的 Loop Engineering 实践是 PR 自动修复循环：

1. **触发**：CI 检测到测试失败，自动触发 Agent 循环
2. **内循环**：Agent 读取失败日志 → 定位问题 → 修改代码 → 运行测试
3. **验证循环**：测试是否通过？通过则提交修复；不通过则反馈错误信息，重新进入内循环
4. **外循环**：修复完成后，将问题模式沉淀到 CLAUDE.md；如果连续多次修复同类问题，触发告警通知人工介入

Boris Cherny 透露，他的团队已在生产环境中长期运行多类专用智能体，它们持续执行诸如重构系统架构、识别并归一化冗余逻辑等任务，并以标准开发流程向代码仓库提交 Pull Request，行为模式与人类工程师高度一致。

### 7.2 SEO 内容生成循环

另一个实践案例是 SEO 内容生成循环：

1. **触发**：每天定时触发
2. **内循环**：Agent 研究关键词 → 生成内容草稿 → SEO 评分
3. **验证循环**：SEO 分 ≥ 阈值则发布；否则反馈优化建议，重新生成
4. **外循环**：监控发布后的流量数据，将表现好的内容模式沉淀为技能

有开发者在分享中提到，他们的 SEO 循环每天自动生成 20-40 个高质量页面，这些页面已经在为公司引流，而他甚至不需要查看它们。

### 7.3 Boris Cherny 的工作流

Boris Cherny 本人的工作流是 Loop Engineering 的缩影：

- **五线并行**：在终端里同时运行 5 个 Claude 窗口，排上 1 到 5 号，开启系统通知
- **多端无缝**：同时在网页端运行 5-10 个 Claude 任务，用 `--teleport` 在本地和云端之间传送进度
- **知识沉淀**：团队共用一个 CLAUDE.md 文件，每周多次更新，发现 Claude 做错了就写规矩
- **计划先行**：先用 Plan 模式和 Claude 来回交流，直到满意它的计划，再切换到自动接受编辑模式

他的核心理念是：**先制定计划，然后迭代完善，再切换到自动编辑**。一个好的计划比一百次盲目的循环更重要。

## 八、局限与挑战

### 8.1 算力成本是核心瓶颈

Loop Engineering 的代价是持续的算力投入。多个循环并行运行、长时间的迭代验证，都需要大量的 LLM 调用。虽然该路径可显著提升研发效率与代码质量，但其背后所需的持续性算力投入远高于常规对话式 AI 应用，由此带来的高昂运维开销，仍是现阶段实现大规模商业部署的核心瓶颈。

### 8.2 循环失控风险

没有良好边界的循环可能失控——Agent 陷入无限重试、在错误方向上越跑越远、消耗大量资源却产出垃圾。设计可靠的停止条件和异常处理机制，比设计循环本身更难。

### 8.3 经验质量管理

Skills 和 Memory 是循环系统变聪明的关键，但错误的经验会被传播放大。如果一次循环沉淀了错误的"经验"（比如一个错误的修复模式被写进 CLAUDE.md），后续所有循环都会被误导。需要引入可信度评分、时间衰减权重和人工抽查机制。

### 8.4 概念炒作的风险

每一个新概念都有被过度营销的风险。Loop Engineering 的核心思想——设计自动化反馈系统——并不是全新的发明，控制论、DevOps、CI/CD 早就在做类似的事情。它的真正价值在于把这套思维方式应用到了 AI Agent 领域。判断它是不是噱头，最好的方式不是争论定义，而是去看真实的工程实现——有人愿意写、有测试覆盖、能合并进主干，那它至少解决了一个真实存在的问题。

## 九、总结与展望

### 9.1 核心洞察

| # | 洞察 | 核心要点 |
|---|------|---------|
| 1 | 范式跃迁 | 从"写 Prompt"到"设计循环"，开发者角色从指令发送者变为循环系统设计者 |
| 2 | 四层嵌套 | Prompt → Context → Harness → Loop，每层包住前一层，杠杆率递增 |
| 3 | 双层循环 | 内循环把任务做好，外循环决定做什么并持续改进 |
| 4 | Loop Stack 六件套 | Automations + Worktrees + Skills + Connectors + Sub-agents + Memory |
| 5 | 循环堆叠 | Agent 循环 + 验证循环 + 支持循环，每层堆叠增加自我纠错能力 |
| 6 | 执行与决策分离 | 执行层不思考，决策层不执行 |
| 7 | 有边界优于开放 | 明确的停止条件是循环可靠运行的前提 |
| 8 | 反馈是燃料 | 没有反馈机制的循环只是空转 |

### 9.2 从 Human-in-the-Loop 到 Human-on-the-Loop

Loop Engineering 带来的最深层变化，是人机关系的转变：

- **Human-in-the-Loop**（人在循环里）：每一步都需要人确认、介入、推进。人成了最忙的节点。
- **Human-on-the-Loop**（人在循环上）：人设定目标、划定边界、处理高风险取舍，但不充当每一轮的调度器。Agent 自主推进，人只在需要时介入。

这并不意味着人变得不重要了——相反，人的角色变得更加关键。人从"每一轮的调度器"升级为"循环系统的设计师"，需要思考的是：什么任务适合自动化循环？什么任务必须保留人工判断？如何设计反馈机制让循环越跑越好？

### 9.3 给不同读者的行动建议

**技术决策者**：评估团队中哪些工作流适合改造为 Loop Engineering 模式。从低风险、高重复的场景入手（如 CI 修复、文档更新、代码审查），逐步积累经验。

**软件工程师**：从改变自己使用 Coding Agent 的习惯开始。不要每次手动输入 prompt，尝试设计一个简单的自动化循环——比如用 cron + Claude Code CLI 自动跑测试修复。把每次循环的经验沉淀到 CLAUDE.md 中。

**产品经理**：识别可以循环化的工作流程，设计"Human-on-the-Loop"的交互模式。建立循环成功与否的度量指标——不是看单次输出质量，而是看系统是否在随时间改进。

---

Loop Engineering 的本质，是把原来靠人手动接力的循环，改造成一个由 Agent 自己推进的工程系统。人仍然要定目标、划边界、判断高风险取舍，但不必再充当每一轮的调度器。

这不是"用 AI 替代人"的故事，而是"人从低价值重复劳动中解放出来，专注于更高层的设计与判断"的故事。正如 Boris Cherny 所说，这是接下来几个月甚至今年剩余时间里，我们会看到的下一次转变。

**当循环开始自己转起来，人的工作就变成了设计更好的循环。**
